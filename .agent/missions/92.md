# Mission 92 — Fuzz testing investigation.

Goal: a fuzzer in `.tmp/` generates random `.ine` files (valid-structure +
mutation), runs ≥1000 iterations against lexer/parser/semantic, and the
crash/resilience findings are recorded in NOTES — an investigation, no source.

Files:
  - .tmp/fuzzer/fuzz.py      (new scratch)
  - .tmp/fuzzer/corpus.ine   (optional seed, scratch)
  - .agent/NOTES.md          (append one section)
  - src/ine/lexer.py, parser.py, semantic.py   (read only)

Steps:
  1. [ ] Write `.tmp/fuzzer/fuzz.py`: a grammar-aware generator that emits
          syntactically plausible Ine (random `make <kind> <id>:` from the
          real dictionary `kind` list, random properties from each kind's
          `properties`, random `inside:` groups, `say` lines, values picked
          loosely) AND a mutator that takes a valid sample and performs one
          random edit (insert/delete/duplicate/reverse tokens, unclosed
          body, bad indent). Seed with `random.seed` fixed per run.
  2. [ ] Run each generated buffer through
          `lex → parse → analyze → resolve → execute` inside a per-case
          `try/except (LexError, SyntaxError, SemanticError, BackendError)` —
          a language-level error is SUCCESS in the harness (resilience),
          while a crash (an exception NOT in that tuple, or a traceback) is
          a finding. The harness must never raise itself: anomalous
          exceptions are captured, deduplicated, and printed with the
          offending input excerpt.
  3. [ ] Execute ≥1000 iterations, keeping the run under a few seconds, and
          record in NOTES `## Mission 92 — fuzz findings` the total count,
          the count of language-level errors (expected), and any anomalous
          exceptions. If zero crashes, say so explicitly — a clean 1000-run
          baseline is a finding, not a reason to keep mutating the same kind.
  4. [ ] If an anomalous exception IS found, isolate the minimal input
          (shrink by deleting whole lines while it still crashes), record the
          exact failure and input in NOTES, and propose the fix as a
          follow-up PLAN item (do not implement here).
  5. [ ] Keep the whole thing in `.tmp/` — the tool is scratch; the findings
          are the durable output in `.agent/NOTES.md`.

Verify: the fuzzer completes ≥1000 iterations with no harness crash of its
own; `git status` shows nothing modified under `src/`.
Done when: NOTES has the iteration/crash table and either a clean 1000-run
baseline or an isolated anomaly.
Do not: fix engine code (an investigation; fixes become follow-up items);
run the fuzzer to exhaustion (a fixed iteration budget only); add pytest
integration; write durable results into `.tmp/`.
