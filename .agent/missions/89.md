# Mission 89 — Extension packaging investigation.

Goal: a written packaging strategy (bundled Python vs. documented
prerequisite, pyodide vs. not) with a working `.vsix` build script in
`.tmp/` — an investigation whose output is the plan in NOTES.

Files:
  - .agent/NOTES.md                   (append one section)
  - .tmp/vsix-packaging/build.ps1     (scratch prototype script)
  - editor/vscode-ine/package.json    (read only)
  - pyproject.toml                    (read only)

Steps:
  1. [ ] Read `editor/vscode-ine/extension.js` `pythonTarget`/`DictionaryWorker`
          to know the runtime dependency: the extension shells out to
          `python <repo>/src/ine/autocomplete.py` (extension.js:22-28). Notes
          that require a workspace root and local Python.
  2. [ ] Document the three candidate distribution strategies in NOTES with
          the trade-offs:
          - **Bundle**: ship a Python runtime (e.g. embedded via
            `python-build-standalone` / `astral-sh/python-build-standalone`)
            plus the `src/ine` source inside the .vsix. Cost: large payload,
            platform-specific builds, Python version pinning.
          - **Require-prerequisite**: document that the user must have Python
            3.10+ installed and set `INE_PYTHON` (extension.js:24). Cost:
            zero bundling, onboarding friction.
          - **Pyodide/WebAssembly in the extension host**: run the engine in
            WASM. Cost: pyodide only ships a `.py` load path that currently
            can't speak the JSON-lines subprocess protocol; validate-limited
            feasibility — this repo has no runtime bridge.
  3. [ ] Write a minimal .vsix build script (`npm install -g @vscode/vsce` or
          `npx @vscode/vsce package`) in `.tmp/vsix-packaging/build.ps1` that
          packages the extension directory. Run it once; confirm a `.vsix`
          artifact is produced (or record the exact failure if `vsce` is
          unavailable — a script that documents the command it would run is a
          valid output).
  4. [ ] In NOTES `## Mission 89 — extension packaging strategy`, record the
          strategy table, the recommended path (prerequisite-documented,
          matching the current `INE_PYTHON` knob), and the open question for
          the commander (whether to eventually bundle). Mark the script as
          scratch, not a durable location.
  5. [ ] Do not change `extension.js` or package.json — an investigation
          produces the plan; bundling is a follow-up mission if approved.

Verify: the script runs (or documents a precise blocker); `git status` shows
no modified editor/ or src/ file.
Done when: NOTES carries the three strategy rows + recommendation and the
