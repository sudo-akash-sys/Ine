# Mission 78 — Multi-backend consistency audit

Goal: a written comparison of how the HTML backend and the visual backend
render the SAME semantic model, with every divergence classified as a bug or
as intentional, recorded in `.agent/NOTES.md`. This mission changes no source
file — its deliverable is the finding.

Files:
  - .agent/NOTES.md             (append one section)
  - src/ine/backend_html.py     (read only)
  - src/ine/backend_visual.py   (read only)
  - src/ine/semantic.py         (read only)

Steps:
  1. [x] Read `src/ine/semantic.py` lines 20–60: `Model.entities`,
          `Model.relationships`, `Model.properties`. These three are the
          entire interface both backends see; nothing else about the model
          may differ between them.
  2. [x] Read `_layout_for_kind` (src/ine/backend_html.py:49) and
          `_render_children` (:147) for the HTML side, and `_layout_of`
          (src/ine/backend_visual.py:59) and `_pack_children` (:237) for the
          visual side. Write down, for each, what `layout: row` produces.
  3. [x] Read `_position_of` (src/ine/backend_visual.py:67) and the
          HTML equivalent (search `position` in backend_html.py). Write down
          what `position: bottom` produces on each side.
  4. [x] Read `_attrs` (src/ine/backend_html.py:126) and `_written` (:110).
          Establish whether the HTML backend honours per-entity properties
          that the program wrote, and whether the visual backend's
          `_render_entity` (:124) reads `model.properties` at all beyond
          `text` and `title`. Record the exact answer.
  5. [x] Read `dictionary.style_declarations` (src/ine/dictionary.py:305)
          and `style_overrides` (:356). Establish which backend calls them.
          Record it.
  6. [x] APPEND a section to `.agent/NOTES.md` titled
          `## Mission 78 — multi-backend consistency` containing a table
          with one row per behaviour (children layout, `position: bottom`,
          written per-entity properties, dictionary style hints) and three
          columns: HTML, Visual, verdict. The verdict cell must be exactly
          `bug`, `intentional` or `unknown`, and `bug`/`intentional` must
          each carry a one-line reason. `unknown` is the honest answer where
          the model does not decide the question — say so rather than
          guessing.
  7. [x] Below the table, list the divergences you judged to be bugs as
          candidate follow-up missions in one line each (headline +
          the test that would pin it). Do not implement them; they become
          PLAN items for the commander to schedule.

Verify: `python -m pytest tests -q` — all pass, and `git status` shows no
modified source file (this mission edits nothing but NOTES.md).
Done when: NOTES.md carries the table with every cell filled, and the
candidate-follow-up list is present.
Do not: change any source file — a divergence you find is recorded, not
fixed; propose new language semantics; write outside the repository.
