# Mission 106 — Integration with other tools research.

Goal: a NOTES integration strategy (IDE plugins beyond VS Code, Make/npm
build scripts, GitHub Actions for CI and rendering) with one prototyped
GitHub Action that renders `.ine` to HTML — research + one sample integration.

Files:
  - .agent/NOTES.md              (append one section)
  - .github/workflows/render-demo.yml  (new — the one prototype integration)
  - .tmp/integration-probe/      (scratch only, if a local demo is needed)
  - src/ine/cli.py               (read only)
  - examples/ (read only)

Steps:
  1. [ ] Read `cli.py` main flags (`ine <file>.ine [-o out.html]`,
          `--native`, `--visual`, `--dict`) and README's documented command
          forms — the integration surface is exactly these. List in NOTES
          the integration targets and their shape:
          - **Build tools**: a Makefile target / npm script that runs
            `python -m ine <file>.ine -o <out>.html` and fails on a nonzero
            exit (build integration = one command; `--native`/`--visual` are
            interactive and NOT CI-safe).
          - **GitHub Actions**: a reusable workflow that checks out, installs
            Python 3.10+, runs the render command, and uploads the html —
            demonstrate with `.github/workflows/render-demo.yml` rendering
            `examples/hello/hello.ine` to an artifact.
          - **IDE plugins (JetBrains etc.)**: the autocomplete JSON-lines
            protocol is language-agnostic (stdin/stdout, 1 query per line);
            document the protocol surface so another editor can reuse it
            (protocol shape from autocomplete.py: `{buffer,line,column,id}` →
            `{line,column,context,items[,id]}`; validate/hover/format when
            items 84 - 85 land).
  2. [ ] Write the sample workflow `.github/workflows/render-demo.yml`
          (push on `main`, `ubuntu-latest`, setup-python@5, run
          `python -m ine examples/hello/hello.ine -o out.html`, upload
          `out.html` as an artifact). Keep it minimal and dependency-free
          (no cache, no matrix).
  3. [ ] Verify the WORKFLOW LOGIC locally as far as possible: run the exact
          render command by hand (builds green, html non-empty). The workflow
          file itself cannot run here — note that its first real execution
          is on push, and keep the YAML to constructs setup-python's action
          supports (no `env.DEBUG`-style invention).
  4. [ ] Record a Makefile-script SAMPLE (not committed) option in NOTES
          with the target body, but do not add a Makefile/npm root script to
          the repo unless one already exists — the strategy is the deliverable.

Verify: `python -m ine examples/hello/hello.ine -o <tmp>/out.html` exits 0 and
produces non-empty html; `git status` shows the workflow + NOTES only.
Done when: NOTES has the three integration rows with the protocol surface,
and the sample GitHub Action workflow is committed.
Do not: change cli.py flags; add a root Makefile; make the workflow run
native/visual targets; invent CI features that do not exist.
