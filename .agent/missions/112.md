# Mission 112 — Visual editor investigation.

Goal: a NOTES proposal for a minimal visual editor for Ine (block or diagram
based, drag-drop containment, round-trip visual↔text) with a `.tmp/`
prototype of ONE interaction — research + scratch prototype, no engine change.

Files:
  - .agent/NOTES.md         (append one section)
  - .tmp/visual-editor-probe/ (scratch prototype only)
  - src/ine/semantic.py     (read only)
  - src/ine/backend_visual.py (read only — reuse its tree-model ideas)

Steps:
  1. [ ] Read `semantic.py`'s Model (entities/properties/relationships/
          groups — the data a visual editor must both read and write) and
          `backend_visual.py`'s tree layout (`_children`, `_pack_children`),
          writing down the exact containment abstractions a canvas would
          render: entity = node, `inside:` = edge, groups = nested regions.
  2. [ ] Compare the two minimal representations in NOTES:
          - **Block-based (Scratch-like)**: stacked statement blocks matching
            the source lines directly — trivial round-trip (block ↔ line)
            but visually noisy.
          - **Diagram-based (nodes + containment)**: hierarchical canvas —
            clean visual but needs a source-mapping for the reverse trip.
          Recommend the diagram form (fits Ine's containment), and state the
          hardest part: **round-trip** — a canvas edit must map to a source
          edit without invalidating the rest of the file. Define the scope
          that makes it feasible: round-trip only for the entities/groups
          the canvas owns (per-entity body editing stays textual).
  3. [ ] Prototype ONE interaction in `.tmp/visual-editor-probe/probe.py`:
          given a parsed Model, render a two-level containment tree as an
          ASCII/HTML canvas (not a real GUI — headless-safe), and implement
          `move(entity, new_parent)` as a Model mutation that regenerates the
          SOURCE text for that entity's `inside:` block (prove: the edited
          source re-parses and `analyze` shows the new parent). Headless, no
          tkinter; a real GUI is a follow-up.
  4. [ ] Write NOTES `## Mission 112 — visual editor` with the
          representation choice, the round-trip scope rule, the probe
          evidence (model → canvas → move → re-parse), the tech options
          (VS Code webview vs. tkinter vs. web app), and the follow-up item
          (a displayable webview spike). Mark the whole feature as
          product-direction territory: commander decides whether a visual
          editor is worth its cost.
  5. [ ] No src/ file changes; the prototype lives in `.tmp/` as scratch.

Verify: the probe's move→source-edit→re-parse round-trip passes; `git status`
shows no src/ change.
Done when: NOTES has the representation choice, round-trip scope, probe
evidence, and the commander-gated follow-up recommendation.
Do not: build a GUI; depend on tkinter display; modify the engine; keep
durable results in `.tmp/`.
