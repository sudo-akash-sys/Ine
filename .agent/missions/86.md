# Mission 86 — Code actions/refactoring investigation.

Goal: a written proposal in NOTES for the highest-value Ine code actions
(extract-to-group at minimum) with a runnable prototype proving one example,
recorded so the executor that builds the real action has no open questions.

Files:
  - .agent/NOTES.md                  (append one section)
  - .tmp/code-actions-probe/         (scratch prototype only)
  - src/ine/parser.py, semantic.py   (read only)
  - editor/vscode-ine/extension.js   (read only)

Steps:
  1. [ ] Read the statement AST surfaces (parser.py statement nodes,
          semantic.py Model: entities/properties/relationships/groups) and
          extension.js's worker/query pattern. Write down, in NOTES, the
          map of statement types to what a text replace must change to be
          safe.
  2. [ ] Enumerate candidate actions for .ine with the rough implementation
          cost for each: extract-to-group (promote a set of consecutive
          child `make`s into a named group), rename entity/kind (all
          referring statements), inline group (flatten a group's children
          into its parent), convert `make 3 card` ↔ three handwritten bodies.
          Record one paragraph each: what it changes, which statements it
          must rewrite, and the text-span basis (line/column in the buffer,
          since the engine has no source mapping).
  3. [ ] Choose `extract to group` as the prototype. Specify its behavior:
          given (entity a, entity b) consecutive siblings under one parent in
          the buffer, produce the replacement text forming a `group` with those
          two entities inside. Write a REPL pipeline in the prototype
          (`.tmp/code-actions-probe/probe.py`) whose `extract_to_group(source,
          ids)` returns the edited source, and verify with the real parse:
          `analyze(parse(lex(edited)))` still yields the same entity kinds and
          create `SayTests`-style equivalences where cheap.
  4. [ ] In the NOTES section `## Mission 86 — code actions investigation`,
          record: the candidate table from step 2, the prototype choice and
          exact rule from step 3, the gap (no source mapping; edits are
          text-level line surgery), and the recommended ordering of the
          remaining actions. Mark the `.tmp` prototype as scratch, not a
          durable location.
  5. [ ] Do NOT implement the action in the editor extension — an investigation
          produces the proposal; the implementation becomes a follow-up PLAN
          item if the commander approves.

Verify: `python -m pytest tests -q` — all pass and `git status` shows no
modified `src/` file (NOTES + `.tmp` only).
Done when: NOTES carries the candidate table, the prototype's exact rule, and
the recommendation; the probe runs.
Do not: add code actions to extension.js; change the language; invent syntax;
write durable results into `.tmp/`.
