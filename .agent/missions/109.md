# Mission 109 — Build system modernization.

Goal: the current setuptools+pytest approach is reviewed, a modernization
decision is recorded in NOTES with concrete measured benefit or "keep
setuptools", and build performance is improved if cheap and safe — research
leaning to "keep", with evidence.

Files:
  - .agent/NOTES.md       (append one section)
  - pyproject.toml        (read only)
  - README.md/BUILD-NOTES.md  (read only)

Steps:
  1. [ ] Measure the current concrete numbers, not impressions: time
          `python -m pytest tests -q` once (record wall-clock) and the suite
          size (534 tests / 18 subtests at Session 48). Record the editable
          install path used today (`pip install -e .`? no install? README's
          instructions), and how `python -m ine` resolves `src/` (README
          shim `ine.py` vs installed console script).
  2. [ ] Evaluate the two modern options against this repo's actual shape
          (one package, no third-party runtime deps, hermetic suite, Windows
          dev):
          - **hatch / rye / uv**: velocity benefits (parallel envs, faster
            resolution, `uv` wheel isolation) vs. cost (tool churn, Windows
            setup, no measured need at one package).
          - **setuptools** (current, pyproject build-system line already
            present): legacy but zero-friction.
          Record a table (option | benefit | cost | verdict).
  3. [ ] Decide: **keep setuptools** with one cheap proven improvement if the
          measurement supports it (e.g. pytest config in pyproject
          (`[tool.pytest.ini_options]`, `testpaths`) and a documented
          `pip install -e .` line so auto new-contributors install once), OR
          switch if a hard defect exists (it does not — suites pass). State
          the recommendation with the measured test time as the baseline.
  4. [ ] If the pytest config/testpaths addition is made, confirm
          `python -m pytest tests -q` still finds every test and the count is
          unchanged (534 / 18 subtests).
  5. [ ] Write NOTES `## Mission 109 — build modernization` with the numbers,
          the options table, the decision and its reasoning, and the
          follow-up triggers (only adopt uv/hatch when a measured pain —
          slow editable install, env churn — appears).

Verify: `python -m pytest tests -q` green and the count unchanged; any
pyproject edit keeps `pip install -e .` working (documented, not re-run if
no network).
Done when: NOTES records the measured baseline, the options table, the keep-
setuptools decision, and the follow-up triggers.
Do not: migrate the build system; add CI; reinstall toolchains; change the
way the suite is invoked.
