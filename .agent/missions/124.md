# Mission 124 — run the executable queue to exhaustion

Area: ine-agent
Depends on: 123
Goal: `ine-agent run` keeps going through the executable queue until there is
nothing left to do, with one attempt per mission, instead of stopping after a
fixed number of cycles or retrying the same failure.

## Why

The default of 20 cycles is arbitrary: it either truncates a long queue or
forces the commander to guess a number. A fixed retry budget turns one
transient failure into two requests for the same mission. And three
notifications per mission is noise; the commander needs the outcome and the
things that need a decision.

## Files

- `src/ine_agent/cli.py` — option surface and defaults.
- `src/ine_agent/supervisor.py` — loop bound, attempt accounting, summary.
- `src/ine_agent/notify.py` — notification set.
- `tests/test_ine_agent.py` — queue, retry, and notification tests.

## Steps

1. [x] In `cli.py`, replace the required-style cycle bound with an optional
   `--max-missions` bound that defaults to unset, and keep `--cycle-limit` as
   a documented alias for it so existing commands and documentation keep
   working. Default `--max-attempts` to 1. An unset bound means "run until the
   queue is exhausted", which is finite because a mission is attempted at most
   once and is then `DONE`, `BLOCKED`, or `DEFERRED`. — `--max-missions` /
   `--cycle-limit` share one `dest`, default `None`; `--max-attempts`
   defaults to 1; the supervisor attribute is `max_missions`.
2. [x] In `supervisor.py`, make the loop terminate when the next mission lookup
   finds no `EXECUTABLE` item, when the mission-number set is exhausted, or
   when the optional bound is reached — never on a wall-clock or cycle
   counter alone. Count a mission once regardless of how many attempts it was
   given. — a `_counted` set keys the bound on mission identity; the stop
   message names the bound and how much of the plan is still EXECUTABLE
   (`_open_queue_count`, read from the plan rather than assumed).
3. [x] Keep continue-on-failure: a mission that fails does not stop the run, and
   does not prevent later independent missions from running. A mission that
   needs the commander is recorded and skipped. — unchanged; covered by
   `test_a_failing_mission_does_not_stop_the_ones_after_it`.
4. [x] In `notify.py` and the supervisor, send exactly one completion
   summary per run: missions completed, failed, refused for a missing index,
   deferred, and the proposed follow-ups. Keep immediate notification for a
   commander gate and for a run that ends with nothing completed. Remove the
   per-mission started and per-mission done notifications. — `_tally` +
   `_completion_summary()` feed the run report, the notification, and the
   run's end-of-run summary line; `_completion_notification()` retitles a run
   that completed nothing; the started/done banners are gone.
5. [x] Make follow-up missions proposal-only. A receipt's follow-up is written
   to the run report and, when it is a real deliverable, appended to the plan
   as a `CLAUDE_REVIEW` item; nothing under that tag is ever executed
   automatically. A worker must not be able to create an `EXECUTABLE` item.
   — `state.propose_follow_up()` appends the item with `PROPOSAL_MARKER`, and
   `Task.executable` is False for any item carrying it, so the plan's own
   parsing (not the worker's intent) is what keeps a proposal unexecutable. A
   proposal that only restates its mission is dropped, and a repeat is not
   filed twice (`content_words` comparison).
6. [x] In `tests/test_ine_agent.py`: a queue of several missions runs to the
   end with one attempt each; a failing mission does not stop the following
   one; `--max-missions` stops after the given count; `--cycle-limit` still
   works as an alias; exactly one completion notification is sent; a follow-up
   is proposed as `CLAUDE_REVIEW` and is not selected by the next run. —
   `QueueExhaustionTests` (7) and `FollowUpProposalTests` (4).

## Finding

- `CLAUDE_REVIEW` is NOT inert in this plan: the selection rule treats it as
  executable and routes it to the claude review pre-pass. Filing a proposal
  under that tag alone would therefore have made the loop pick it up on the
  next run, refuse it for want of an index and tag it `BLOCKED` — turning a
  suggestion into a blocker. The marker, checked by `Task.executable`, is what
  actually makes it inert.
- The refused count and the mission tallies are separate: a refusal happens
  outside a cycle, so a run that refused everything has a full tally of zeros
  and a non-zero refusal count. Reporting only the tally would have said
  "0 completed, 0 failed, 0 blocked, 0 deferred" and hidden the outstanding
  planner work.

## Constraints

- Preserve the plan, the index files, and the verification discipline.
